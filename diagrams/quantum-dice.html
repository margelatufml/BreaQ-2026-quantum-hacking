Quantum Dice: Random or Rigged?

The startup claims its bits are fair and safe because they come from a quantum circuit. We put one classical bug into the service: it re-seeds on every request, so it hands out the same 1,024 bits every time. A balanced histogram cannot see this; a replay check can.

The project at a glance

  2. bugThe serviceClean keeps its generator. Faulty re-seeds on every request.

1 · The question and the threat model

We will investigate whether re-seeding the simulator with the same seed on every request can cause identical "random" batches across requests, and whether a cross-request replay check can detect it.

ItemOur answerIn plain words
Protected propertyFreshness: every request returns new bitsNo customer gets bits that were already handed out.
FaultThe service re-seeds the simulator with its fixed seed on every requestOne line of classical code in the wrong place; not a quantum effect.
Trusted componentsThe one-qubit model, Qiskit's Statevector, our auditorWe assume these work correctly.
Auditor accessBits only, in order, with request boundariesThe auditor is like a customer: no seeds, no source code.
ExclusionsReal hardware, physical entropy, certification, cryptographic securityWhat we do not claim to test.

Prediction: the fault should break freshness, while the share of ones still looks normal. It held.

  1. quantum

    The coin: sample(n, rng)

    IN
    n = 1,024 and a random generator (or a seed number)
    DO
    Start one qubit in |0⟩, apply H to get an equal mix of 0 and 1, measure. Repeat n times, keeping the order.
    OUT
    a string of n bits, e.g. 111001011000…

    Why: by the Born rule each result has chance (1/√2)² = 1/2. A fair batch is rarely exactly 512 ones: 95% of batches have between 481 and 543.

    COIN = QuantumCircuit(1)
COIN.h(0)

def sample(n, rng):
    sv = Statevector(COIN)
    sv.seed(rng)
    return "".join(sv.sample_memory(n))

    P(0) = P(1) = 0.5
    95% band: 481–543 ones per 1,024

  2. classical

    Clean service: Clean(seed)

    IN
    a seed, given once when the service starts (e.g. 7)
    DO
    Creates one random generator and keeps it, so every request continues the same stream.
    OUT
    a new batch on every request

    Why: this is the correct pattern, like creating rng = np.random.default_rng(7) once at app start-up and reusing it.

    class Clean:
    def __init__(self, seed):
        self.rng = np.random.default_rng(seed)

    def request(self):
        return sample(BITS, self.rng)

    Clean(7), request 1: 111001011000001111110010… 507 ones
    request 2: 101010111001001000001001… 504 ones
    different every time

  3. bug

    Faulty service: Faulty(seed)

    IN
    the same seed
    DO
    Re-seeds on every request, so the stream restarts from the beginning each time.
    OUT
    the same batch on every request

    Why: like calling random.seed(7) inside the request handler. Control: with the same seed, Clean and Faulty give the same first batch, so the only difference is when the generator is created.

    class Faulty:
    def __init__(self, seed):
        self.seed = seed

    def request(self):
        return sample(BITS, self.seed)  # BUG

    Faulty(7), request 1: 111001011000001111110010… 507 ones
    request 2: 111001011000001111110010… 507 ones
    identical every time, and equal to Clean(7) request 1

  4. check

    Frequency check: frequency_alarm(bits)

    IN
    one batch
    DO
    Counts the ones, then an exact binomial test asks: how surprising is this count for a fair coin? The answer is a p-value.
    OUT
    True (alarm) if p < 0.01, which happens when a batch has 470 ones or fewer, or 554 or more

    Why: this is the "is it 50/50?" test the startup's claim invites. It would catch a biased coin, but it cannot see a replay, because a replayed batch looks like any normal batch.

    def frequency_alarm(bits):
    return binomtest(bits.count("1"),
                     len(bits)).pvalue < 0.01

    507 ones → p = 0.78 → no alarm
    470 ones → p = 0.0095 → alarm
    on fair bits it alarms 0.946% of the time

  5. check

    Replay check: replay_alarms(batches)

    IN
    all batches of one service, in request order
    DO
    Remembers every batch it has seen in a set. A batch that is already in the set raises an alarm.
    OUT
    one True or False per request

    Why: two fresh 1,024-bit batches are equal with chance 2⁻¹⁰²⁴, so in practice never. Any exact repeat is a real replay, and there is no threshold to tune.

    def replay_alarms(batches):
    seen, alarms = set(), []
    for bits in batches:
        alarms.append(bits in seen)
        seen.add(bits)
    return alarms

    Faulty(1000) → [False, True, True, True, True, …]
    Clean(1000) → [False, False, False, False, False, …]
    the first answer is always False: nothing to compare with yet

  6. classical

    Evaluation: evaluate(seeds)

    IN
    20 seeds, one service instance per seed
    DO
    For Clean and for Faulty: 20 instances × 50 requests = 1,000 batches. Both checks run on every batch; alarms are counted and replay misses noted by position.
    OUT
    alarm counts per service and check, plus where replay missed

    Why: it runs on two seed sets, like a train/test split. Tuning seeds 0–19 check the false-alarm rates; evaluation seeds 1000–1019 are fresh data that was never looked at.

    for Service in (Clean, Faulty):
    for seed in seeds:
        service = Service(seed)
        batches = [service.request() for _ in range(REQUESTS)]
        alarms = replay_alarms(batches)
        freq += sum(map(frequency_alarm, batches))
        replay += sum(alarms)

    Clean → frequency 13, replay 0
    Faulty → frequency 0, replay 980
    replay misses by position: {0: 20}

How to read the table

Clean batches should stay silent and faulty batches should raise an alarm. A false alarm is a clean batch flagged (a false positive), a detection is a faulty batch flagged (a true positive), and a miss is a faulty batch not flagged (a false negative).

Why the frequency check sees nothing

A faulty batch is a genuine fair sample; the bug is only that it comes back again. The 20 faulty batches in the evaluation had 477 to 532 ones, all inside the silent zone of 471 to 553. Counting ones cannot see a repeat across requests.

The 20 misses

Every miss is request 1 of a faulty service. The first batch is the original, and a replay can only be recognised once there is something to compare it with: {0: 20}.

1,000 faulty batches are really 20

Inside one faulty service all 50 batches are copies, so the independent evidence is 20 services. Replay caught 20 / 20 from request 2 onward; frequency caught 0 / 20. Twenty cases is a small sample, and the report says so.

Are 13 false alarms a problem?

No. On fair bits the frequency check alarms 0.946% of the time, about 9 per 1,000 batches, so 8 and 13 are normal variation. Replay had 0, as expected when a chance match has probability 2⁻¹⁰²⁴.

Why two seed sets

Like a train/test split. Both thresholds were fixed in advance: the usual 1% level, and the exact-match rule has no parameter. The tuning set only confirmed the false-alarm rates; the evaluation set is fresh, and nothing was changed after seeing it.

4 · Words you need

Qubit
A bit that can be in a mix of 0 and 1 until it is measured.
|0⟩
The qubit's starting state: definitely 0.
Hadamard gate (H)
Turns |0⟩ into an equal mix of |0⟩ and |1⟩.
Measurement
Reading the qubit. It gives 0 or 1, and the mix is gone.
Born rule
The chance of each result is its amplitude squared: (1/√2)² = 1/2.
Seed
The starting number of a pseudorandom generator. The same seed gives the same sequence.
Generator
The object that produces the pseudorandom stream. Keeping it continues the stream.
Request and batch
One call to the service, which returns one batch of 1,024 bits.
Freshness
Every batch is new: nobody gets bits that were already handed out.
Replay
Serving bits that were already served.
Binomial test and p-value
How surprising a count of ones is for a fair coin. p < 0.01 means less than a 1% chance by luck.
False alarm, detection, miss
False positive, true positive, false negative.
Tuning and evaluation set
A train/test split: report the numbers from the fresh set only.
Pseudo-replication
Counting copies of the same evidence as if they were independent cases.

5 · Predict a new case

The jury may change one thing and ask what happens. Our answers:

  • Bigger batches, 2,048 bits?Frequency still alarms on about 1% of clean batches and still misses the replay. Replay still flags every faulty request from the second one on: an exact copy does not depend on size.
  • The service re-seeds only on every 10th request?Requests 1–10 are fresh, then 11–20 replay 1–10, and so on. Replay flags 40 of 50 requests per service and misses the first cycle of 10.
  • A new seed on every request, but a guessable one (seed + request number)?Every batch is different, so replay never fires and frequency passes. Yet anyone who knows the scheme can regenerate every batch. Our checks cannot see predictability; only fixing the seeding can.
  • The replay is shifted by one bit?Exact matching misses it, because the batch is no longer an identical string. It would need a substring or similarity check.
  • A biased coin with P(1) = 0.6?That is the frequency check's job. About 614 ones are expected, far above 554, so almost every batch alarms; replay stays silent.

6 · Recommended response

  1. Fix the cause: create the generator once per service lifetime from OS entropy and never re-seed per request. Add a test that two requests differ.
  2. Monitor: run the replay check inside the service and stop serving bits when it fires.
  3. Detection is not repair: every batch served since the bug is compromised. Tell consumers and regenerate anything derived from it.

Limitations

  • Simulation only: pseudorandom bits, not physical entropy. Distinct seeds do not prove independence.
  • One fault and one batch size; the faulty evidence rests on 20 distinct batches.
  • Replay misses the first faulty request, shifted or partial replays, and output that is unique but predictable.
  • An alarm means "investigate", not "an attacker is present". Passing our checks proves nothing about quantumness or security.

Say it to the jury

  1. The faulty service gave perfectly balanced bits, 477 to 532 ones per 1,024, and passed the frequency check every time: a balanced histogram proves nothing.
  2. Our replay check caught all 20 faulty services from their second request, with 0 false alarms on 1,000 fresh clean batches.
  3. It cannot see bits that are unique but predictable, so the real fix is seeding the generator once from OS entropy.
