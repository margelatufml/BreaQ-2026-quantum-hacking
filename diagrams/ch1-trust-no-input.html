Three versions of the same fingerprint

The reversed key always equals the registry, so the circuit is fine. Only the cases with a non-identity map fail. The two calibration cases read the same backwards and use the identity map, so they could never show the bug.

The fix

  1. Decode from the counts only: take the majority key and reverse it.
  2. Compare with the registry. Never pass the map into the decision.
  3. Fail closed: a tie, an empty result or a malformed key gives MISMATCH.
  4. Use the map afterwards, only to format the display.

The exploit

An attacker who can edit only the map can reorder bits but never create or delete a 1. A target is reachable only if it is an anagram of the source.

1s in the source01234
Reachable targets14641
Maps that change it (of 24)01820180

Worst case, a false accept: an asset that really encodes 1100 is reported as 0011 with map (2,3,0,1), so it would match a registry entry of 0011.

Say it to the jury

  1. Same counts with a different map gives a different decision: the metadata decides, not the qubits.
  2. The circuit and the measurement are correct in every case; the bug is a display step inside an authorization check.
  3. Validating that the map is a permutation proves its shape, not that it is safe to use in a security decision.
